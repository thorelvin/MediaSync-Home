# 0A.4 — SQLite-arkitektur og kapasitetsbevis

## Mål

Måle én-database- og to-databasekandidater uten å opprette endelig produktskjema, og dokumentere kapasitet ved minst én million filposter.

- `docs/PERFORMANCE.md`

- `spikes/0a4_sqlite_capacity/**`
- `tests/spikes/0a4_sqlite_capacity/**`

- spike-, status- og beslutningsrapportene

`schema/catalog.sql` og `schema/recovery.sql` forblir blokkerte plassholdere.

## Eksperimenter

1. Minimal én-databasekandidat med differensiert durability.
2. Minimal to-databasekandidat med durable handoff og recoveryavstemming.
3. Krasj før/etter kritiske databaseoverganger.
4. Backup/restore og migrasjonskompleksitet for begge modeller.
5. Bulkinnlasting av minst én million file entries samt coverage/representative indekser.
6. Database-, indeks- og WAL-størrelse.
7. Peak RSS og representative query plans/P95.
8. AppData-vekst, minimum fri plass og `SQLITE_FULL`-oppførsel.
9. Kode-/testkompleksitet og antall nødvendige recoverytilstander.

## Kvalitetsport

- Rådata og kommandoer er vedlagt.
- Kandidatene bruker samme logiske invariants og sammenlignbart datasett.
- Ingen plassholder-SQL gjøres autoritativ.
- Codex kan anbefale ett alternativ, men ADR-003 forblir maksimalt `RECOMMENDED` til eiergodkjenning.
- Codex stopper etter 0A.4.
